# Developing ASUFC Finance

- Extend the React, TypeScript and Vite frontend and the FastAPI, Psycopg and PostgreSQL backend in place. Follow the conventions of the surrounding module. Register protected financial endpoints before including the router and use parameterized SQL.
- Keep financial calculations and writes authoritative on the server. Use integer cents, database transactions and the existing locks for financial mutations. Separate received cash, purchasing credits and expected funds. Only confirmed receipts become spendable. Validate eligibility, expiry, year, available funding and budget on the server, including for imports and corrections.
- Preserve transaction history and record reasons for adjustments, duplicate overrides, corrections, voids and transfer reversals. Exclude voided purchases from active spending. Keep reports consistent and distinguish internal ledger reconciliation from bank reconciliation.
- Preserve staff session, cookie and mutation protections. Use authorized paths for file access. Bound and validate spreadsheet uploads and prevent formulas in exported untrusted text. Keep credentials, real spreadsheets and private records out of Git, CI, the demo and test fixtures.
- GitHub Pages uses Actions to publish only the Vite Pages-mode artifact at `/ASUFC/`. Keep demo operations in memory, fictional and free of backend calls. The staff build uses the authenticated API.
- Base future AI queries on approved, scoped deterministic functions. Keep external providers disabled pending approval, keep keys on the backend and require staff review of every proposed write. Never execute generated SQL or send real records or receipts to an external model without authorization.
- Use disposable databases and fictional data. Run `npm test`, `npm run build`, `npm run build:pages` and `npm run test:pages` from `frontend/`. Run `python -m pytest -v` from `backend/` with the disposable PostgreSQL environment from `.github/workflows/ci.yml`. Run `npm run test:e2e` against the disposable stack. Run dependency, gateway, backup and restore checks as defined in CI.
- A change is complete when the normal entry points work, applicable tests run successfully, balances and access boundaries are verified, the documentation reflects the implementation and pending decisions are recorded. Verify the live browser and deployed entry point for Pages changes. Preserve user changes, avoid force-pushing, and keep production deployment subject to approval.
